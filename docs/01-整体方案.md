# Mac 一键清理应用 · 整体方案

> 基于开源项目 [tw93/Mole](https://github.com/tw93/Mole) 封装的原生 macOS 图形应用
> 版本：v1 方案 · 待确认

---

## 一、项目目标

把 Mole 的命令行清理能力，封装成一个**极简的原生 Mac 应用**。

用户只需做一件事：**点一下圆圈按钮**，然后看着进度跑完，最后看结果。

| 需求 | 实现方式 |
|---|---|
| 点一下就开始清理 | 单按钮，无二级菜单，无参数配置 |
| 列出清理过程 | 圆环下方实时滚动展示「正在清理哪个模块 / 哪个项目」 |
| 圆圈按钮 + 边圈进度 + 百分比 | 环形进度条，中心显示百分比数字 |
| 完成后显示清理结果 | 圆环收口变绿 + 结果面板（释放空间 / 清理项数 / 磁盘剩余） |

## 二、技术可行性（已实测验证，非推测）

动手前我先把你本机环境跑通了，四个关键前提**全部通过**：

| # | 验证项 | 结果 | 意义 |
|---|---|---|---|
| 1 | `swiftc` 能否编译 SwiftUI 应用 | ✅ 通过（需 `-parse-as-library`） | **不需要装完整 Xcode**，产物仅 56KB |
| 2 | `.app` 打包 + 签名 | ✅ 通过（ad-hoc 签名） | 能产出真正可双击运行的应用 |
| 3 | Mole 清理流程耗时 | ⏱ 实测 dry-run **50 秒** | 决定了进度条必须平滑，不能只有 14 格 |
| 4 | 能否捕获 Mole 内部进度 | ✅ 通过（见下） | **关键突破，方案基石** |

### 关于第 4 点（最重要）

Mole 的清理逻辑是 bash 脚本。我实测发现它用 `BASH_SOURCE[0] == $0` 做了入口守卫，这意味着**可以在不修改 Mole 任何一行源码的前提下，把它的内部函数接管过来**：

```bash
source clean.sh                    # 加载，但不执行 main
declare -f start_section           # ✅ 可见
declare -f safe_clean              # ✅ 可见
start_section() { 发进度事件; 原函数 "$@"; }   # ✅ 覆盖成功，事件正常注入
prompt_for_system_clean() { ... }  # ✅ 可覆盖 → 实现无人值守
```

**这一步的价值**：进度不是靠"猜"或解析终端文本，而是 Mole 主动上报的结构化事件。上游改文案也不影响我们。同时能直接读到 Mole 的结算变量 `total_size_cleaned`、`files_cleaned`、`total_items`，结果**精确到字节**。

## 三、技术选型

**原生 SwiftUI，不选 Electron。**

| 方案 | 体积 | 启动 | 依赖 | 结论 |
|---|---|---|---|---|
| **SwiftUI 原生** | **~1MB** | **瞬开** | 无 | ✅ **选它** |
| Electron | 150MB+ | 1-2 秒 | 需下载运行时 | ❌ 清理工具做成 150MB 说不过去 |

用原生还有个隐藏好处：清理类工具最怕"被清理的对象自己在运行"，原生应用内存占用低、不干扰清理过程本身。

## 四、架构设计

```
┌─────────────────────────────────────────────┐
│  CleanApp.app   (SwiftUI 原生 · 无依赖)      │
│                                             │
│   ┌──────────────┐      ┌────────────────┐  │
│   │  圆环进度 UI  │◄─────┤  EventStore    │  │
│   │  + 日志列表   │      │  (主线程状态)   │  │
│   └──────────────┘      └───────▲────────┘  │
│                                 │ JSON 事件   │
│                        ┌────────┴────────┐  │
│                        │ ProcessRunner   │  │
│                        │ (读取 stdout 流) │  │
│                        └────────▲────────┘  │
└─────────────────────────────────┼───────────┘
                                  │ 启动
                    ┌─────────────┴──────────────┐
                    │  driver.sh (进度注入层)      │
                    │  · source Mole 的 clean.sh  │
                    │  · 覆盖进度函数 → 发 JSON    │
                    │  · 覆盖 sudo 询问 → 无人值守 │
                    └─────────────┬──────────────┘
                                  │ source
                    ┌─────────────┴──────────────┐
                    │  Mole 上游源码 (GPL-3.0)     │
                    │  内置打包，不做任何修改       │
                    └────────────────────────────┘
```

**分三层，职责清晰**：
- **Mole 上游**：原封不动内置。将来 `git pull` 就能升级，不用重新适配。
- **driver.sh**：我们唯一的"胶水层"，负责把内部执行过程翻译成 JSON 事件流。
- **App**：只懂 JSON 事件，不懂 Mole 细节。UI 和执行彻底解耦。

## 五、进度模型（这是交互的核心）

Mole 的清理分 **14 个模块**，但各模块耗时差异极大——`Developer tools` 要几十秒，空的模块 0.1 秒就过。如果简单按"14 格"推进，进度条会**一顿一顿地跳**，甚至卡死不动。

所以采用**双层进度**：

| 层级 | 驱动源 | 作用 |
|---|---|---|
| **主进度（环）** | 14 个模块的加权完成度 | 决定百分比数值 |
| **平滑层** | 收到模块开始事件后，用缓动函数向该模块的目标值平滑推进 | 保证进度**匀速、不倒退、不卡死** |

具体规则：
1. 模块开始 → 环推进到该模块的起始刻度（实时反馈，点了就有动静）
2. 模块内部 → 平滑缓动至该模块的 90% 上限（**绝不提前到 100%**）
3. 模块结束 → 补满到 100%，进入下一个模块
4. 权重按实测耗时分配（`Developer tools` 权重高，空模块权重低）

另外做**两阶段划分**：扫描阶段（0→15%）+ 清理阶段（15→100%），因为 Mole 前 50 秒里相当一部分花在扫描计算上。

## 六、交互流程

```
① 待机              ② 清理中              ③ 完成
┌──────────┐      ┌──────────┐        ┌──────────┐
│          │      │   ╭──╮   │        │   ╭──╮   │
│    ○     │  →   │  ╱ 47%╲  │   →    │  ╱ ✓  ╲  │
│          │      │  ╲    ╱  │        │  ╰────╯  │
│  点击开始 │      │   ╰──╯   │        │ 释放2.4GB │
│          │      │          │        │          │
│          │      │ 清理日志  │        │ 结果明细  │
│          │      │ 滚动中…  │        │          │
└──────────┘      └──────────┘        └──────────┘
   灰色环            渐变环            绿色环+打勾
```

**待机**：圆环静止，中心提示"点击开始清理"。鼠标悬停轻微放大。

**清理中**：
- 圆环边圈随进度增长（青色→蓝色渐变）
- 中心显示实时百分比
- 下方日志区逐行滚动：`▶ 开发者工具` → `  · npm 缓存  已清理 128MB`
- 右下角小字显示已释放空间（实时累加）
- 圆环可点击 → 中途取消（二次确认）

**完成**：
- 圆环变绿 + 打勾动画
- 结果卡片：**释放空间 / 清理项数 / 磁盘可用空间**
- 两个按钮：`完成` / `查看详情`（展开完整清理清单）

## 七、安全设计

删文件的操作，安全必须摆在明面上：

| 措施 | 说明 |
|---|---|
| **沿用 Mole 的安全校验** | 路径合法性、保护共享/系统目录，全部由上游负责，我们不绕过 |
| **清理历史留痕** | Mole 自带 `operations.log`，应用内可查看"上次清理了什么" |
| **保护清单** | 支持 Mole 的 whitelist，把你不想清的目录保护起来 |
| **权限最小化** | 默认**只清用户级**（不需要密码）；系统级缓存作为可选项 |
| **首次运行说明** | 第一次打开明确告知：会删除什么、不会碰什么 |

**关于密码**：Mole 清系统级缓存需要管理员权限。v1 建议**默认跳过系统级**，走完全免密码的顺滑体验；等基础版跑稳了，再在 v2 加"包含系统缓存"开关（届时用 macOS 原生授权弹窗）。

## 十、已确认的决策（v1 定稿）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | **应用名** | **Sweep** |
| 2 | **清理范围** | 只做用户级，**全程免密码** |
| 3 | **主按钮行为** | 点击**立刻开始清理**，不做预览拦截 |
| 4 | **Mole 集成** | **内置源码，完全自包含**（约 1MB，无外部依赖） |

### 这些决策带来的具体约束

- **免密码**（决策 2）→ 在 driver 层直接跳过 Mole 的系统级清理询问，不做任何授权弹窗。实测数据显示可回收空间基本都在用户级，这个取舍划算。
- **立刻清理**（决策 3）→ 待机态不设"预览"步骤，圆环点击即是唯一入口。安全兜底依赖 Mole 自身的路径校验 + 应用内的 whitelist 保护清单。
- **自包含**（决策 4）→ 产物是一个独立 `Sweep.app`，内置 Mole 源码，拖到任何 Mac 上都能直接跑。
- **名称 Sweep**（决策 1）→ 图标用一个简洁的环形/扫掠造型，与圆环进度按钮同构。发布时附 GPL-3.0 许可及 "Based on Mole by tw93" 来源说明。
